A finished system is not defined by reaching any of the statistical performance objectives. It is defined by correct,

0.3 Build implementation rule
Prefer the thinnest viable code above proven libraries. Use Python for the application control plane and
supported high-performance native libraries for heavy computation; add custom Rust only after a measured
bottleneck and tests justify it. The historical simulator is one chosen pinned NautilusTrader API version, not a
second custom matching engine. No backend stack switch without a documented architecture decision (ADR).

0.4 Scope of the research claim
  •     “Search all timeframes and combinations” means systematic bounded coverage of supported spaces, not
        mathematical exhaustive enumeration of infinitely many parameter values.
  •     “Billions” refers at most to possible cheap mathematical combinations. Never label a candidate a full
        detailed backtest unless it actually received the declared event replay. Performance is measured, not
        promised.
  •     “No degradation” means invariant preservation in exact reference tests and declared numerical
        tolerances for genuine floating-point computations; nothing can guarantee all future workloads become
        faster without tradeoffs.
  •     “No hallucinations” means unverified model output cannot enter authoritative results or trusted software
        releases; no language model is guaranteed never to make a mistaken statement.

Build an original, installable research product — not a competing backtester. Codex constructs the initial
repository and proves it with tests; Hermes Factory owns the dashboard, research orchestration, candidate
definitions, validation workflow, experiment audit trail, and automation policy. It reuses NautilusTrader for
detailed event-driven historical simulations where it passes an acceptance benchmark; DuckDB + Apache Parquet
for data; SQLite for durable operational records; standard scientific libraries for statistical tests; and the existing

Hermes Agent for maintenance and research management. Custom Rust is added only for narrow, measured hot
paths where it materially improves throughput without changing results. Optional Python bridges the existing
NautilusTrader APIs and statistical tools.

The product should feel like one application even when a local worker process executes a backtest. This is a
modular monolith with isolated workers, not a microservice cluster and not five unrelated applications.
Everything authored for the project lives in one private GitHub repository. Third-party packages are pinned and
installed by an idempotent installer, not copied wholesale into that repository.

1.1 Non-negotiable design principles
  1.     Reuse before building: evaluate an existing maintained, license-compatible library before writing
         equivalent code.
  2.     Correctness before throughput: baseline/reference test fixtures and invariant checks must pass before a
         speed optimization is accepted.
  3.     One source of truth: data versions, strategy specifications, fill assumptions, results, and provenance are
         immutable and reproducible.
  4.     Minimal justified stack: no infrastructure service without a demonstrated requirement.
  5.     Separation of concerns: deterministic research jobs do not depend on an LLM being available.
  6.     Continuous operation, bounded resources: the system may be active 24/7, but should not burn 100% CPU
         or send 24/7 LLM requests unnecessarily.
  7.     Evidence, not guarantees: pass/fail status and uncertainty are explicit, including when a claimed target
         cannot be shown.
  8.     No silent promotion: untested revisions cannot replace the known-good application automatically.

The default dashboard maintains five ranked, distinct candidates for each instrument, giving 40 target
leaderboard slots. Each candidate may use any supported single timeframe or combinations of timeframes.
Rankings are instrument-specific; one pair's success must not erase results for another. If fewer than five viable
experiments exist, display available candidates and clearly mark the empty positions: never invent results. Even
candidates below the 70% win-rate aspiration remain ranked; 70% is a continuing research goal, not an entry
condition.

Each candidate is assigned immutable IDs and a status: EXPERIMENTAL, SIMULATED, VALIDATED,
INSUFFICIENT_EVIDENCE, FAILED_CHECKS, or ARCHIVED. Dashboard rankings must visibly distinguish
a high score from strong validation evidence. An archived prior leader remains in history even after replacement.

2.2 Historical periods and sample-size goals
  •       2025: 2025-01-01 00:00 UTC through 2025-12-31 23:59:59 UTC, subject to actual market trading sessions and
          data availability.
  •       2026: 2026-01-01 00:00 UTC through the latest complete, verified tick/bar actually available at the time of
          each import. On the specification date (2 November 2026), no unverified claim is made about each symbol's
          most recent tick.
  •       At least 50 completed historical trades in each period per strategy is the user-defined frequency target.
          For 2026 this means 50 from 1 January through the current latest data, not a presumed full year.
  •       Report 2025, 2026-to-date, pooled, and evaluation-only metrics separately. Do not mix unverified training
          performance into out-of-sample statistics.
  •       Data acquisition increments from the last successfully committed partition instead of re-downloading full
          history.

The primary research period remains only 2025–2026, as requested. Optional older market data may be held in a
separate research-context area, disabled by default, and must never be silently added to acceptance statistics. Two
years (one incomplete) are insufficient for certainty about all market regimes.

2.3 Strategy families
The research framework supports mean reversion, trend following, momentum, breakout, reversal, range/volatility
patterns, session/time-of-day behavior, and multi-family confirmations. Hermes can propose new hypotheses and
variations; they enter the same auditable pipeline. No strategy family is automatically assumed profitable.

Initial timeframe menu should cover available minute and hourly intervals ( M1, M5, M15, M30, H1, H4, D1)
and additional granularities only when the provider and simulator support them. Intraday signals can use higher-
timeframe confirmations, but the higher-timeframe bar must be closed and observable at the decision timestamp.
A daily timeframe may yield few under-24-hour positions; that is reported, not worked around by distorting data.

3. Scope boundary and realistic success criterion
This version provides historical simulation, signal research, independent validation, and paper observation. It
must not be treated as autonomous broker execution software. The source PDFs sometimes describe MT5 Expert
Advisor generation, demo forwarding, and real-money deployment. In this consolidated blueprint, MT5 may be used
later as a read-only comparison or manually supervised demo-observation environment, subject to separate
review; live order placement, real-money portfolio management, and autonomous broker deployment are not
included.

The user's requirement that conservative tests should be equal to or worse than later live results is a desired
hypothesis to test, not an attainable 100% guarantee. Spread/slippage stress guards one type of simulation
optimism; it cannot predict future market regimes, liquidity conditions, timing, or order fills. The platform should
measure baseline versus stress discrepancies and report whether observed future paper-market conditions fall
within assumed ranges.

Success = accurate, repeatable, well-audited research, resilient 24/7 operations, honest top-five rankings, and
clear measurement of uncertainty. Not a claim of certain returns.

6. Data system: acquisition, fidelity, storage, time
6.1 Data importer workflow
  1.    Read desired instrument, data interval and last validated timestamp from the manifest.
  2.    Retrieve only missing provider partitions with retries, bounded batch size, rate-limiting and cached source
        artifacts.
  3.    Save raw bytes, content hash, fetch time, source URL/identifier, exact date bounds, schema version, and
        retrieval outcome.
  4.    Decode without rounding bid, ask, timestamps, quote volumes, or source precision.
  5.    Normalize timestamps to UTC while retaining source time semantics. Never silently infer timezone on
        ambiguous records.
  6.    Validate chronological ordering, missing intervals, duplicate ticks, inverted spreads, unreasonable quote
        jumps, out-of-session artifacts, and malformed records.
  7.    Distinguish expected market closure/weekends from true data gaps. Record gaps instead of automatically
        inventing ticks.
  8.    Write verified, partitioned Arrow/Parquet datasets with ZSTD; validate row counts, ranges and hashes after
        reading back.
  9.    Atomically mark a partition committed and update its latest-complete timestamp.
  10.   Produce aggregated timeframes deterministically from the canonical stream; record whether each bar is
        bid-, ask-, or midpoint-based and whether it is complete.

Partitioning: instrument / year / month / day (choose practical size through disk benchmarks). Avoid storing one
giant JSON file or loading a full year of ticks into memory. Stream bounded batches; use Parquet row-group sizes
determined by benchmarks. Cache derived features with a key including dataset checksum, formula version,
parameter hash and timestamp policy.

6.2 Source contract

Source data must contain or permit deriving: timestamp_utc, instrument_id, bid, ask, optional quoted
volume, provider ID, and revision metadata. Historical ticks are provider-specific quotes, not guaranteed executable
prices at every broker. For unavailable historical bid/ask detail, mark reduced fidelity and do not falsely label it tick-
verified.

Initial candidate is Dukascopy through dukascopy-node, which documents historical bid/ask tick output and
filesystem caching. Validate XAUUSD availability, dates, current endpoint function and service terms in a pilot run.
Keep a provider abstraction for later independent comparison without installing another warehouse.

6.3 Instrument registry
For each instrument, store price precision, tick size, defined pip size (if applicable), quote/base currencies, contract
multiplier, point value, margin-rate assumptions, permitted volume steps, min/max trade sizes, timezone/session
calendar, and XAUUSD-specific conversion. These values are scenario-specific, versioned, and may not represent
every broker. UNKNOWN_SPEC blocks instrument-dependent money or risk calculations.

6.4 Disk and cache policy
Estimate actual 2025–2026 tick disk usage before bulk download. The user accepts a large full-resolution archive;
nevertheless the VPS disk size has not been supplied. Installation must fail gracefully or pause with a storage
warning if capacity is inadequate, rather than silently drop records. Keep data in losslessly compressed Parquet, but
do not promise a compression ratio. Raw files may be purged only after verified conversion and a recoverable
backup/source manifest exists; preserve original artifacts where licensing and disk allow. Every prune is logged.



6.5 Lossless canonical data contract (hard gate)
Store the provider's original source bytes or an independently verified reversible canonical capture; keep the
original download checksum and license/access metadata. Canonical quote schema should include at least:
instrument_id, event_ts_utc_ns (or exact source-resolution UTC timestamp with precision metadata), bid_int,
ask_int, price_scale, source_id, ingest_batch_id, original_record_order, quality_flags, and optional
quote volumes only when actually supplied. Do not invent a nanosecond precision source if the provider
reports milliseconds. Fixed-point conversion must be reversible on all captured sample values, including Gold and
JPY pairs; otherwise use an exact decimal representation with a documented source-scale mapping.

Validate: bid<=ask unless explicitly flagged as corrupt; monotonic ingestion ordering with source-sequence tie-
break for equal timestamps; duplicates categorized rather than blindly dropped; missing-day/market-session
calendars; price/tick-size agreement; nonnegative spread except explicitly quarantined exceptions; timestamp
range; DST conversion; stale price/outliers; tick-source metadata. A suspicious quote is quarantined and counted,
not overwritten with a smoothed guess. Data quality failures prevent a run from being marked validated.

Use Parquet with a measured, not assumed, scheme: partition by instrument and suitable week/month boundaries;
column projection, statistics and row-group pruning; a bounded file size; ZSTD lossless compression starting with
low levels. Benchmark ZSTD level 1–3 against Snappy for compressed bytes, cold/read-cache throughput and CPU.
Avoid per-day microfiles when they create high metadata overhead. Periodic atomic compaction keeps the original
source version and checksum lineage; an immutable manifest maps current logical partitions to file hashes.

Multi-timeframe derivation: derive M1/M5/M15/M30/H1/H4/D1 from canonical verified quotes once, with explicit
candle-end timestamps, provider session boundaries and available_at timestamps. For signals using higher-
timeframe confirmation, use only a bar that was closed and available at the decision time. Recompute warm-up
windows across incremental imports; never treat a partially completed H1 or D1 bar as finalized.

No repeated full history downloads: use incremental acquisition checkpoints with time overlap for reconciliation,
then compare old and new overlapping source quotes. Corrections make a new dataset version and invalidate
affected downstream caches. Import pacing respects source availability and usage terms. The 2026 end timestamp is
always the last verified record actually ingested, not the wall clock.

6.6 Four-tier versioned caching strategy
  1.    L1 bounded worker RAM: active immutable arrays with LRU or clock eviction and explicit memory cap;
        cache hits and evictions observable.
  2.    L2 disk feature artifacts: derived bars/indicators/signal primitives stored in portable columnar files;
        content-addressable keys include source-data manifest, source time range, feature/operator version,
        parameters, input timeframe, available_at rules, instrument spec version and code revision.
  3.    L3 experiment outcome cache: exact completed run result referenced by an experiment fingerprint;
        reusing a run does not increment completed-run counts; new data, new execution assumptions or new
        validation rules require new IDs.
  4.    L4 Linux OS page cache: rely on file system caching rather than implementing a duplicate universal data-
        cache server. The application reads local Parquet column projection and Arrow batches; Arrow memory-
        mapped IPC is opt-in only where benchmarked.

8. Simulation fidelity, orders, and the 2/2 cost model
8.1 Preserve historical quotes
Observed historical bid and ask are the authoritative quote inputs. Never alter archived quotes. In the conservative
scenario, derive synthetic pessimistic bid/ask quotes only in memory:

mid = (bid_observed + ask_observed) / 2
spread_actual = ask_observed - bid_observed
spread_effective = max(spread_actual, 2 * pip_size)
bid_test = mid - spread_effective / 2
ask_test = mid + spread_effective / 2
If actual spread is greater than 2 pips, use the actual greater spread. If a source provides only midpoint candles,
label the result MIDPOINT_APPROXIMATION and attach the spread assumption, not REAL_BID_ASK.
Preserve original raw data and model version.

8.2 Slippage separate from spread
For appropriate simulated market and stop-market fills, apply an adverse two-pip price adjustment per fill in the
conservative scenario, respecting instrument increment rounding and buy/sell direction. An opening and closing
market order can therefore experience two separate adverse adjustments. Avoid making a generic limit order fill
worse than its price limit; model its chance of not filling rather than violating limit-order semantics. Document the
fill rules explicitly and cover with unit tests.

NautilusTrader's basic L1 probability-based slippage model may be one tick, not a fixed 2 pips. Do not misconfigure
one tick as two pips. Inspect the chosen version's extension API and use a thin tested custom fill adapter only if
needed; keep actual matching/order state in NautilusTrader. Use a scenario ID so all candidate results can be
reproduced.

8.3 Stop/target logic and 1:3 semantics
  •     Risk/reward refers to intended price distances at signal entry, not a guarantee of realized net payout.
  •     Entry, stop and target must be rounded to legal instrument tick increments with explicit rounding direction.
  •     A trade is not opened when stop distance, minimum volume, minimum stop level, or margin makes it
        impossible to satisfy the declared simulated risk budget.
  •     Stop and target touch order must be established from available tick sequence; if both are touched inside an
        unresolvable bar, use conservative treatment or classify uncertain, never silently favor TP.
  •     Position mark-to-market uses appropriate bid for long liquidation and ask for short liquidation.
  •     Gaps/halts can lead to fills beyond stop expectations; the -1R nominal stop is not guaranteed.
  •     24-hour deadline uses monotonic event time. Record late data or no executable quote as an anomaly.
  •     A single unified execution assumption is applied in both annual scenarios and pooled scenario, not hand-
        tuned on evaluation sets.

8.5 Fill-adapter interface and golden arithmetic examples
The original quote stream is immutable. The conservative pricing layer uses an effective spread floor:
S_eff=max(S_observed,2*pip_unit) with symmetric widening around the observed mid when required; it is
not an extra 2 pips piled onto every recorded spread. Apply up to the configured adverse 2 pips separately to
eligible market or stop-market executions, with sign correct for buy versus sell; never worsen a limit fill beyond its
specified limit. Instrument pip unit and rounding must be explicit, including JPY-cross decimals and Gold
convention. Log observed bid/ask, effective bid/ask, spread uplift, separate per-fill slippage adjustment, eligibility,
order type, signal time, execution time, and exit reason.

Intended 1:3 R:R is measured in price distance, not guaranteed realized net R. In an illustrative liquid case with
two pip-spread quotes at each fill, market entry and market exit can have an aggregate six-pip adverse round-trip
difference relative to unchanged midpoints (two pips total spread cost + two pips slippage each at entry and exit).
This is an explanatory arithmetic example, not a rule that every order has six pips in costs: fill type, spread changes,
limit execution, source quotes, and price path alter the actual result. Never impose slippage on an imaginary trade
execution at an unavailable time.

9. Simulated risk, account arithmetic, and reporting
9.1 Sizing definition

9.4 Top-five rule precisely

Each instrument has top_5_all, which retains five highest-quality available candidates even if every one is below
70% or fails one of the targets. A secondary validated_only view shows the qualifying subset; this can legitimately
have 0–5 candidates. Never mix the two or label unvalidated winners as validated.

Proposed ranking after grouping candidates by validation tier:

  1.    Validation tier: sound/independent-evidence candidates above insufficient-evidence or failed-integrity
        candidates. An invalid or fabricated result must never rank as trustworthy.
  2.    Historical pessimistic-model win rate, with uncertainty/sample-size visible and a minimum credible
        sample gate for a 'validated' status.
  3.    No simulated insolvency, then fewest worst consecutive losses (prefer <=5) and explicit recovery evidence.
  4.    Pessimistic-model ending balance for equal win rate and losing-streak score.
  5.    Winning-streak length, then robustness/recency and a deterministic ID tie-break.

Because raw win-rate differences of 0.1% are often noise, the dashboard should show whether confidence intervals
substantially overlap rather than imply a definitive superiority. Ranking policy and version must be recorded.
Similarity-aware diversification (e.g., avoid five parameterizations producing almost identical signals) can be a
visible secondary shortlist filter, not a hidden override of the requested top five.

9.6 Strategy diagnostic and improvement factory (mandatory)

9.7 Stop / take-profit search and execution sensitivity
Stop distances are discrete instrument-legal values constrained by provider/instrument minimums, observed price
ranges and a predeclared training search interval. For each stop candidate, set initial TP distance to exactly 3 ×
initial SL distance before tick rounding, and validate the tick-rounded ratio under declared numerical policy.
Recompute hypothetical position size and cash risk for the specific distance. Evaluate under identical reference and
conservative fill rules; report changes to win rate, realized R, missed targets, trade frequency, 24h forced exits, min-
volume rejections, stop-first fractions, MAE/MFE histograms and risk concentration. Do not silently select new stops
based on the same final holdout.

Keep favorable-then-reverse and immediately-stopped trades separately visible: these patterns suggest different
research questions. It is not correct to conclude that a wider stop or a shorter target is automatically better. The
fixed 1:3 requirement precludes simply reducing TP while leaving SL unchanged.

9.8 Portfolio and per-strategy simulation distinction
Each independent strategy candidate gets its own starting simulated $20 scenario and per-year reset report; pooled
chronological simulation is shown separately. The sum of eight independent strategy equity curves is not a single
executable $20 portfolio. If a research scenario combines multiple simultaneous simulated positions, explicitly
enforce and report aggregate margin/exposure limits and drawdown; no implicit infinite leverage. One-open-
position-at-a-time per candidate is the simplest first acceptance profile; alternative overlap policies require a
separately versioned experiment configuration. Stop-loss adverse gaps may exceed intended 10% risk; a five-loss
historical streak cannot guarantee freedom from ruin.



10. Scientific validity: avoid winning by cheating
10.1 2025 and 2026 walk-forward protocol
  •     Apply time-ordered splits. Do not shuffle price observations.
  •     The user's chosen cadence is 3 months: rolling or expanding training segments, then a subsequent
        approximately 3-month out-of-sample window wherever the available sample allows.
  •     For 2025, begin with an initial training window in 2025 and assess subsequent forward windows. For 2026,
        only use information available at each fold's cut-off. On a partial latest quarter, label as PARTIAL_FOLD.
  •     Run both yearly summary views independently plus cross-year chronology. Overlapping trades at cut-offs
        must not leak outcomes to training. Explicit purging/embargo rules apply where labels overlap.
  •     A candidate failing a specified OOS gate is marked OOS_FAILED, not silently accepted. It can remain

        keeping the best five even below goal.
  •     Preserve a final untouched contiguous holdout segment for candidate confirmation when practical. Once it
        is repeatedly inspected or used for selection, it is no longer untouched; reset its designation and explain the
        limitation. Only two recent years makes this more important.

  •     Parameter sensitivity and mild perturbations (not brute-force reranking on OOS).

Acceptance principle: An optimization must not improve the headline score by excluding losing events, changing
the sample after observing results, assuming impossible fills, or altering the denominator. Failed checks must
remain visible.



10.3 Frozen experimental evaluation contract
Karpathy-style research benefits from a fixed evaluator: Hermes or Optuna can propose candidate specifications
inside a designated training partition, but cannot modify the source data, cost assumptions, engine build, scoring
denominator, final holdout or WFO fold boundaries while interpreting the result as the same experiment. A change
to any of these creates a new evaluation_contract_id, new experiment hash, invalidated cross-version rankings
and an audit note. Never quietly rank two versions as apples-to-apples.

Test windows must be selected chronologically before evaluating candidates. Reserve a final untouched segment
where feasible, explicitly accounting for the fact that 2026 is incomplete. On a continuously changing 2026 feed, no
newly arrived observation is unseen after it is used repeatedly to select candidates. Maintain train_only,
selection_oos, final_holdout_unseen, holdout_consumed, and paper_forward tags. OOS failure means
rejected from validated_only, not deleted from all-candidates history.

Use Wilson intervals for win proportions; report numerator/denominator; include hypothesis-testing adjustment or
selection-bias estimates for many correlated trials where applicable. Sharpe and Deflated Sharpe alone do not
establish a reliable advantage; beware a tiny, heavily leveraged $20 simulation. Assess robustness to minor valid
parameter changes, latency/cost sensitivities and yearly/regime changes. Purge trades whose outcomes overlap split
boundaries and apply embargo where labels overlap. Keep sample counts for each fold.

10.4 Negative evidence and screening audit
Maintain the complete number of attempted candidates and all failures, including preprocessing failures. Do not
delete “bad” experiments or only save top-five winners. A random reproducible sample of screened-out candidates
is elevated to full simulation, and the resulting false-negative rate is displayed. Cached runs are reused but not
reclassified as new independent evidence. Statistical confidence does not improve merely because the same data
were recomputed many times.

10.5 Independent verification of diagnostics
MFE/MAE must be recomputable on a small independent reference path with known bid/ask sequence and marked
quote timing. Golden fixtures include: immediate stop; favorable excursion then stop; near-target reversal;
long/short asymmetry; intrabar stop/target ambiguity; 24h censored trade; missing-tick segment; 1:3 stop variants;
parent-child strategy mutation; no false improved status from reused OOS; and empty-trade-set handling. Every
simulation-to-dashboard metric has a trace back to source events.

11.4 Job states and recovery

QUEUED -> CLAIMED -> RUNNING -> CHECKPOINTED -> COMPLETED or FAILED_RETRYABLE /
FAILED_FINAL / CANCELLED. Use immutable run IDs, leases and idempotent result writes. Worker crashes
return expired leases to queue without duplicate accounting. Backups are tested for restore. Data write is atomic:
temporary partition -> validation -> rename/manifest commit.



11.5 Durable scheduling details and state-machine correctness

Scheduler heartbeat/checkpoint frequency is configurable and modest. Recommended initial job states: QUEUED,
CLAIMED, RUNNING, CHECKPOINTED, COMPLETED, FAILED_RETRYABLE, FAILED_FINAL,
CANCELLED, STALE; retention of failure details is permanent. Job leases have UTC expiry and worker identity,
capped retries and exponential backoff. The coordinator uses transactionally claimed work and idempotent upserts
by immutable experiment/run ID; after a process crash, an expired lease is reclaimed rather than duplicated. Long-
running data imports checkpoint per verified partition; a partially written Parquet file must never appear in a
committed dataset manifest.

Coordinator priority classes: integrity/recovery > ingest new source partitions > required holdout/validation > fair
instrument coverage > improvement diagnosis > cheap search > optional performance maintenance. Detect
starvation. Bound Optuna proposal counts per cycle, diagnostic child depth, screen batch size and total in-flight
memory. When data provider, LLM or disk is unavailable, skip/degrade the affected class but keep unrelated
deterministic work active.

24/7 operational loop: the services remain available, resuming work whenever configured budgets and valid
datasets permit. It is acceptable to idle when waiting for new data or quotas. Never create loops that endlessly
regenerate identical candidate definitions or spin while no eligible research exists. Use dry-run and pause
capabilities. Store daily summaries and more detailed weekly reports. Hermes may supply ideas periodically, not
drive all optimization via chat tokens.

  4.    Ollama vs Nous cloud: no local LLM, GPU, Ollama or downloaded weights. Hermes Agent hosted models
        only when authorized and available.
  5.    Two extra pips spread vs 2-pip floor: use the effective floor, not duplicate counted bid/ask costs.
  6.    “Pips” on Gold: define verified XAUUSD tick/pip-equivalent convention per data/instrument profile; no
        universal invented value.
  7.    100% future performance match: cannot be guaranteed; stress testing only reduces some assumptions-
        based optimism.
  8.    “Billions of strategies” claim: separate cheap combination checks from actual event/tick replays; no
        fabricated throughput.
  9.    Repair vs discard poor strategies: all failures remain, systematic MFE/MAE path analysis and parent-child
        improvement are mandatory.
  10.   Initial builder vs future operator: Codex builds/tests/releases, Hermes installs/operates/maintains
        after successful handoff.
  11.   All combinations vs finite resources: cover supported timeframes/families systematically with budgeted
        search; do not imply finite compute can exhaust infinite parameter space.
  12.   Hypothetical risk vs feasible position size: keep $20/10%/1:3 as user scenario but skip trades that violate
        volume/margin risk constraints; no fake fills.
  13.   Search only 2025–2026 vs validation independence: training and evaluation periods must remain inside
        2025/2026, but repeated experiments reduce independence; report limitations and use new paper
        observations for later confirmation.
  14.   Reference vs pessimistic: store and show both; rank primarily using pessimistic scenario, with accuracy
        and validation tiers above raw win rate.

21. Precise handoff contracts and copy-paste commands
21.1 Required scripts and expected behavior
  •    scripts/doctor.sh: read-only by default, checks environment, 4vCPU/8GB resource suitability, free disk,
        pinned tools, source/Nous access if configured, config validation, data availability and current release; exits
        nonzero for unmet required prerequisites; prints human-readable and machine-readable report.
  •     scripts/install.sh: idempotent versioned release installation; asks for owner-supplied credentials using
        secure mechanism; maintains /var/lib state; deploys systemd; does not start unbounded data download or
        research until verified and authorized; prints expected API URL without inventing a public domain.
  •     scripts/verify.sh: local validation and integrated synthetic scenario test, Golden paths + schemas +
        health; records hash and actual results. Options to run extended tests separately.
  •     scripts/benchmark.sh: real representative workload, warm/cold timing, CPU/RSS/disk and compare
        engine screening implementations. Never substitutes synthetic throughput for real event replay
        throughput.
  •     scripts/update.sh and rollback.sh: snapshots existing state and uses tagged releases; executes
        migrations and health checks before swap; preserves last known good and recovery log; never silently
        rewrites canonical data.
  •     scripts/backup.sh, restore-test.sh: verified consistent DB/artifact/archive manifest backups, restore in
        isolated test area.
  •     scripts/create-admin.sh: securely provisions initial admin credentials, no defaults in source code or
        logs.
  •     scripts/seed-fixtures.sh: installs tiny synthetic licensed-safe quote fixtures, never disguises them as
        source market data.
  •     scripts/release-verify.sh: checks manifest, dependencies, test report and signed/hashed release
        provenance.

21.2 Documentation that must be usable by a nontechnical owner

README.md starts with a one-page summary: what is implemented; what is not; supported host; how to open
dashboard; how to pause/resume; how to export and understand validation labels; what to do after a reboot; where
to find alerts; and what needs owner action. The operator guide explains empty leaderboards, sample-size warnings,
missing XAUUSD data, source gaps, free-model quotas and why conservative simulation cannot guarantee future
profits. Troubleshooting commands must distinguish safe read-only checks from actions that change installed state.

21.3 Agent instructions embedded in repo

AGENTS.md addresses Codex: build in small working vertical slices; pin dependencies and legal source access;
maintain semantic invariants; run tests and report actual failures; do not skip end-to-end paths; create a private
repo only after GitHub authorization; do not fake benchmarks; never implement live-money execution.
HERMES_AGENT_INSTRUCTIONS.md addresses Hermes: verify exact tag and original build report; use the
app API to operate; suggest typed hypotheses; rerun scientific checks; respect owner approvals on core code
changes; preserve failed experiments and run IDs; keep hosted AI nonessential to deterministic operation; maintain
one repository and one dashboard.
